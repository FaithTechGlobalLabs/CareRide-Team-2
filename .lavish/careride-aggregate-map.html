01 / Proposed domain model

Ownership follows invariants.

These are design candidates inferred from the SQL and checked against the SQL API. They are not a claim that the application already implements DDD aggregates. A root controls writes to its children; a foreign key or ON DELETE CASCADE alone does not establish that boundary.

Strongest evidence

RideRequest

Child: dispatch records for this ride. Owned values: pickup/destination snapshots, passenger count, accessibility needs, status and pickup/dropoff flags.

Invariant

At most one accepted dispatch per ride. An accepted assignment must name the same driver on the ride and dispatch. Claiming, withdrawing and cancelling must update the relevant records atomically.

Evidence & limits

The unique partial index enforces “at most one”; the claim transaction enforces assignment agreement on that path. CHECK constraints tie flags to status. The schema alone does not enforce agreement between the two tables.

[S1, S3] · ride_requests, dispatches; accept/cancel/withdraw handlers

Conditional grouping

Driver

Candidate children: vehicles and availability rules. Both depend on a driver for their lifecycle and both are read to decide whether the driver can claim a ride.

What would justify the boundary?

A rule that eligibility edits and ride claims must observe a coherent driver state, or a future rule such as “availability intervals may not overlap.” Every participating write must use shared concurrency control.

Tradeoff

One driver boundary simplifies coordination but serializes that driver’s edits. Today’s seat/radius/date checks are mostly local to a row; Vehicle and Availability can remain separate roots if no cross-child invariant needs atomic enforcement.

[S2, S4] · drivers, vehicles, driver_availabilities; eligibleSql

Separate workflow

DriverVerification

References a driver, an approving organization and an optional reviewer. It has its own document, status, expiration and review lifecycle. Prefer a separate root rather than placing every organization’s review under Driver.

Local rule candidates

Review status, reviewer, time and rejection reason should agree. SQL restricts the status vocabulary; the reject handler requires a reason. A general transition policy is not encoded by the schema.

Cross-boundary consequence

Claim eligibility reads approvals. If rejection/revocation must exclude a concurrent claim, verification writes must join the same coordination protocol as that claim.

[S2, S4] · driver_verifications; approve/reject handlers

Potential new concept

Trip / RoundTrip

No Trip table exists. Two ride rows share trip_group_id and point to each other through linked_ride_id. Creation currently inserts both and links them in one transaction.

When it becomes a root

If two legs must always be edited, cancelled or validated together, introduce a Trip root with ride legs as children. Otherwise keep each leg as its own RideRequest root and coordinate paired creation in the application.

Current limits

Cancellation and acceptance act on individual legs. The self-FK ensures an existing target, but does not enforce reciprocal links, exactly two legs, matching groups or return-after-outbound time.

Organization is a tenant boundary, not automatically one giant aggregate.Staff, clients, addresses and rides reference an organization. Keep Organization, Staff, Client and Address as small roots unless a specific multi-entity invariant requires grouping. An organization-wide root would make unrelated bookings and profile edits compete for the same lock.
Supporting aggregate candidate

NotificationSettings → PushSubscription

notification_preferences is keyed by (user_id, kind). Subscriptions reference that composite key. If enabling push must atomically register a device and update preferences, these form a sensible settings aggregate.

Today registration uses separate statements. Disabling push may validly retain subscriptions, so “disabled means no subscriptions” is not an existing invariant. Endpoint uniqueness is global, and account reassignment needs coordination between settings owners.

[S6, S7] · 002_notifications.sql; subscription handler

Independent work

Notification & PushDelivery

A Notification is a small root with exactly one staff or driver recipient. A PushDelivery is a worker record keyed by (notification_id, endpoint), referencing both Notification and PushSubscription.

Prefer an independently updated delivery work item rather than loading every delivery as a Notification child. Retries and delivery status do not determine whether a ride assignment is valid. Some notification rows are written in ride transactions today; push delivery runs afterward.

03 / What “fresh” actually requires

A root needs a concurrency protocol.

Loading a root and its children gives you a view of their state. It does not stop another transaction changing those children. Strong consistency comes from atomic writes, database constraints, and participating writers agreeing on locks or versions. A root can be one entity; it does not need children to qualify.

Decide which moment the invariant must hold.“Eligible when the claim is ordered” differs from “eligible for the entire future ride.” A later expiration, rejection or schedule edit can invalidate an existing assignment even if the original claim was correct. An always-valid-assignment rule needs those later edits to reject, reassign or cancel affected rides too.

Explore the claim / eligibility race

Illustrative interleaving inferred from the SQL paths; this is a reasoning example, not a reproduced failing test.

Protect the ride

Lock the ride before claiming, check its status, assign the driver and write the accepted dispatch in one transaction. Keep the unique accepted-dispatch index as a database backstop. Withdrawal/cancellation must participate in this same lifecycle.

This is already substantially reflected in the SQL handlers.

Coordinate eligibility only where required

If concurrent eligibility edits must be ordered with acceptance, have claims and every relevant vehicle, availability and verification write lock a shared driver/eligibility row. Re-read eligibility after acquiring it, then commit assignment atomically.

Use a consistent lock order when both driver and ride are locked. A shared eligibility-version CAS is another option only if every contributing edit updates that version. Serializable transactions with retry can provide a serial order, but do not make future eligibility changes harmless.

Notification / delivery		Recipient XOR CHECK; one work row per notification/endpoint pair; worker leases due rows. External send and result update are separate. Small boundaries, explicit coordination.Reference other roots by identity and retain snapshots where history matters. Keep dispatch assignment strongly consistent with its ride. Treat matching/search and push delivery as views/work that can lag, then revalidate authoritative state when executing a business command. Reliable asynchronous handoff would need an explicit outbox/event strategy; none is inferred solely from these schemas.
