01 / Proposed ownership

Which roots does the code support?

Strongest multi-entity candidate

RideRequest → Dispatch

Only one driver wins a claim. An assignment and its accepted dispatch must agree. Withdrawing reopens the ride and expires the accepted dispatch together; cancellation changes the ride and expires that dispatch together.

Ride status, pickup/dropoff flags and completion timestamp are local ride state. Pickup requires the assigned driver and approved status; dropoff requires in-progress status and pickup. Route guards and SQL checks protect complementary parts of these rules.

Keep assignment records inside this boundary; an exported dispatch history can be eventual. Do not put Driver, Client, Address or Notification inside it.

routes.ts:901 (claim), :834 (cancel), :971 (transitions), :1062 (withdraw). 001_schema.sql:213, :246.

Plausible / limited evidence

Driver → Vehicle

Registration requires vehicle details and creates driver and vehicle in one transaction. Driver deletion removes vehicles. A vehicle that exists only as this driver's capability record is a reasonable child.

The code does not show a continuing collection-wide rule across vehicles, availability and verifications. Do not infer “exactly one vehicle” or “no overlapping rides”: neither is enforced here. SQL allows multiple vehicles, eligibility uses any matching one, and presentation selects one without recording the chosen vehicle on the ride.

routes.ts:1104, :33 (eligibleSql), :219. personal.ts:122. vehicles has no UNIQUE(driver_id).

Small independent root candidate

DriverVerification

Own the submitted document, expiry and review result: status, reviewer, reviewed timestamp and rejection reason. Approval/rejection changes these fields together and is scoped to the reviewing organization.

The Organization and Driver are referenced roots, not parents that must contain every verification. Current eligibility requires any approved, unexpired verification for that organization; it does not require all document types to pass. The approve/reject handlers do not restrict the prior status.

routes.ts:1177, :1435, :1455; eligibleSql:33. This is a workflow root even though its state currently fits in one row.

Small independent root candidate

AvailabilityRule

Keep recurrence kind, applicable date/days, time window, timezone, active flag and service area together. End must follow start; radius must be positive; one-time/weekly/monthly fields must agree.

There is no rule comparing all availability rows or preventing overlaps. A root per rule is sufficient for demonstrated invariants. A DriverSchedule aggregate becomes useful if rules later depend on the whole schedule or its reservations.

routes.ts:1238, :1302. 001_schema.sql:driver_availabilities CHECK constraints.

Command-level coupling

NotificationSettings → PushSubscriptions

Key by (user_id, kind). Prompt decisions update related flags together. Enabling a browser registers its endpoint and enables push / dismisses the prompt: those changes can reasonably form one atomic settings command.

Today endpoint registration and preference changes use separate queries. Endpoint uniqueness and reassignment span owners and need explicit coordination. Disabling push may retain endpoints; removing a device does not disable push globally. Do not invent an invariant equating push_enabled with subscription count.

notifications/sqlApi.ts:35, :141, :156. notifications/events.ts:54 handles the first-ride prompt in the JSON path.

Independent roots / worker state

Organization, Staff, Client, Address, Notification

Organization is a tenant/lifecycle root; the code gives no ongoing rule requiring all its staff, clients, locations and rides to be children. Staff's role allowlist is local account validation, not a rule over the organization's staff collection.

Client owns profile/contact values and the 50-character notes limit. Address owns location values and active status. Notification owns recipient/content/read state; exactly one staff or driver recipient is required. A PushDelivery is an independent technical work item keyed by notification + endpoint, with atomic lease/retry state.

routes.ts:508, :549, :617, :644, :1510. adminContoller.ts:28. push.ts:39. 001_schema.sql:262.

02 / Fresh reads are not enough

Acceptance is the critical decision point.

The available-rides list can lag. The accept command must recheck the authoritative ride and eligibility inputs: requested/unassigned/future pickup, organization approval, sufficient seats, wheelchair capability and a matching active availability rule. The SQL API does recheck these in the claim UPDATE.

Current protection covers competing claims for one ride.The handler locks that ride with FOR UPDATE. It does not lock verification, vehicle or availability rows, and those edit paths do not share a driver guard. At PostgreSQL's default Read Committed isolation, a statement reads a committed snapshot; another eligibility edit can commit before the claim transaction finishes. No runtime database isolation override was verified.
1 / Claim begins

Ride is locked. The eligibility statement sees an approved verification.

2 / Review changes

A separate transaction rejects that verification and commits independently.

3 / Claim commits

The ride and dispatch can commit based on the earlier eligibility view.

If that ordering is unacceptable, coordinate claim and eligibility edits under a shared driver guard, or a serializable transaction strategy with retries covering the relevant reads and writes. Simply putting objects in a Driver class changes no concurrency guarantee. A shared guard preserves smaller roots but introduces explicit command coordination and some contention.

The business decision: eligible when?

At acceptance: check authoritative inputs in an agreed concurrency order, then retain the commitment even if availability later changes. No continuous synchronization of every assigned ride is implied.

Through pickup/completion: rejecting verification, reducing vehicle capacity or deleting availability must also reject the change, invalidate/reassign affected rides, or prevent pickup as required. The code does not implement this stronger policy. First define its reaction and timing; then design the coordination.

Expiry is currently checked against CURRENT_DATE, not the future pickup date. “Approval must remain valid on pickup day” is an additional rule. No double-booking rule appears in the eligibility predicate.

Evidence: routes.ts:29–75, :901–955; availability edits :1302; verification review :1435. PostgreSQL isolation documentation.

04 / Cross-root workflows

Two places to resist a giant aggregate.

Round-trip booking

Creation writes both legs, shared group ID and reciprocal links in one transaction. Partial creation should not be exposed as a successful round trip.

After creation, each leg can be independently accepted, cancelled or completed. No same-driver, coupled cancellation, or return-after-outbound rule is enforced.

Use a booking creation transaction with independent RideRequest roots for the current behavior. A Trip/Booking root owning both legs becomes a stronger candidate if the business requires continuing cross-leg invariants. Atomic creation alone does not establish lifelong ownership.

routes.ts:743, :773–818; each state command filters one ride ID.

Organization / driver deletion

personal.ts refuses deletion if an affected ride is in_progress, then updates many collections. That is a genuine cross-root lifecycle rule, not evidence that an organization owns all those objects inside one aggregate.

A future SQL implementation can coordinate deletion and ride start/claim with a common lifecycle guard, or mark deletion pending, block new activity, drain assignments and purge afterward. Existing active rides must be checked authoritatively.

The JSON update queue only serializes its own process. It does not coordinate PostgreSQL ride writes, so today's mixed store paths cannot provide that cross-store guarantee.

personal.ts:59, :84–174; jsonStore.ts:372; routes.ts:991.

05 / Evidence limits

Do not mistake mixed paths for a finished model.

  • Active entry point: index.ts:13 mounts registerApi. Main ride and notification APIs use PostgreSQL. personal.ts deletion uses JSON.
  • adminContoller.ts: its staff list/find/update/delete helpers throw postgresUnused. The controller is not mounted by the inspected entry point. Its role allowlist does not establish a currently enforced authorization model.
  • organizationController.ts: creates Organization and first Staff through separate queries. The mounted /organizations/register route instead uses one atomic SQL CTE. Initial account creation merits atomicity, but no “always at least one staff/admin” rule is implemented.
  • events.ts: reconciliation is invoked by JSON-store updates. Its broad notifications and first-ride prompts are not wired into the SQL claim path. SQL's notifyStaff inserts narrower messages directly.
  • Subscriptions: registration changes subscriptions and preference flags through separate statements. Push delivery has an external send/ack gap despite atomic leases.

The analysis follows the requested files plus their store, helper, schema and entry-point dependencies. No application code changed and no runtime concurrency tests were run.
